# 取引先マスタ 外部API取得セットアップ手順（torihikisaki-enrich Edge Function）

会社情報を外部API（**Sansan Data Hub** / 国税庁 法人番号Web-API / gBizINFO）から取得するための
サーバー関数「**torihikisaki-enrich**」を Supabase 上に置く（初回のみ）。

- 外部APIへは**読取のみ**。この関数がDBを書き換えることはしない。
- 取得値は画面で**提案**として出し、**空欄だけ**を候補にする。採用は人が選び、通常の保存経路（＝変更履歴に残る）を通る。
- **口座・反社（承認制の項目）はAPI自動投入の対象外**。
- キー未設定でも関数はエラーにならず「未接続＋理由」を返す。画面は手入力で動き続ける。

> 🔴**この関数は「本番」Supabase に置きます。** 学習用DBには `user_roles` も Auth ユーザーも無く、
> 関数内のロール判定（admin/accounting）が通らないためです。
> 取引先データの読み書きは学習用DB、外部API呼び出しは本番の関数、と役割が分かれます。

---

## 1. Secrets の設定

Supabase ダッシュボード（**本番プロジェクト**）左メニュー **Edge Functions** → 上部 **Secrets** タブ。

### 🔴 Sansanは認証方式が2系統ある（お持ちのキーで決まる）

| | Sansan Open API（名刺管理） | Sansan Data Hub Change Feed |
|---|---|---|
| 必要なもの | **APIキー1本**（32桁） | client_id ＋ secret ＋ 会社フィードID |
| Secret名 | `SANSAN_API_KEY` | `SANSAN_CLIENT_ID` / `SANSAN_CLIENT_SECRET` / `SANSAN_COMPANY_FEED_ID` |
| 取れる会社情報 | 社名・**郵便番号・住所**・電話・FAX・URL | 左記＋法人番号・資本金・従業員数・売上・上場区分・T番号・SOC |
| 会社専用API | **無い**（名刺経由でのみ取得） | 会社フィードあり |
| 検索キー | **会社名**（法人番号での検索は不可） | SOC / 法人番号 |
| レート制限 | **10回/秒** | — |
| 仕様 | https://docs.ap.sansan.com/ja/api/openapi/v3.1/index.html | — |

**APIキー1本しかない場合は `SANSAN_API_KEY` だけ設定**すれば動きます。
埋まるのは6項目（うち**必須3＝正式社名・本社郵便番号・本社住所**）。
現在「入力できない必須項目」だった**本社住所が埋まる**のがこの経路の実利です。

他のAPIは届き次第、同じ場所に追加すれば動きます（画面側の改修は不要）：

| Secret名 | 用途 | 状況 |
|---|---|---|
| `NTA_APP_ID` | 国税庁 法人番号Web-API（**法人番号・商号・登記住所**） | アプリケーションID申請中（9月上旬見込み） |
| `GBIZINFO_TOKEN` | gBizINFO（代表者名・資本金・**建設業許可の有効期限**） | トークン即時発行・未申請 |

> ⚠️ `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` の設定は不要（自動注入）。
> ⚠️ Secretの値は**このリポジトリに書かない**（Publicリポジトリです）。

## 2. デプロイ（ダッシュボードから・CLIなし）

1. **Edge Functions** → **「Deploy a new function」→「Via Editor」**
2. 関数名に **`torihikisaki-enrich`** と入力（この名前でないと呼べません）
3. エディタの中身を全部消し、`supabase/functions/torihikisaki-enrich/index.ts` の中身を貼り付け
4. **Deploy** を押す
5. 関数の設定で **「Verify JWT」が ON**（既定）であることを確認

## 4. つまずきやすい点

| 症状 | 原因と対処 |
|---|---|
| `Function が未デプロイの可能性` | §2 のデプロイが未実施、または関数名の綴り違い |
| `APIキーが無効か、権限がありません` | `SANSAN_API_KEY`（32桁）を確認。前後の空白混入に注意 |
| `認証に失敗しました（HTTP 401/400）` | Data Hub の client_id / client_secret を確認 |
| `レート制限（10回/秒）` | Open API の制限。少し待って再実行 |
| `会社フィードの取得に失敗（HTTP 404）` | フィードIDが会社以外（拠点・人物・名刺）の可能性 |
| `取得結果: 0行` | その期間に更新が無いだけ。`--days 30` で広げて再確認 |
| `403 取得権限がありません` | ログインユーザーのロールが admin / accounting 以外 |

## 5. 🔴 Change Feed の性質（Data Hub を使う場合のみ・実装方針に関わる）

Sansan Data Hub の Change Feed は**差分API**です。「この1社を今すぐ引く」用途には向きません
（期間内に更新がなければ返ってきません）。

したがって実運用は次の形にします（§3の調査結果を見てから確定）：

1. **定期同期**：Change Feed を定期取得し、キャッシュテーブルへ蓄積（増分）
2. **画面はキャッシュを引く**：SOC・法人番号で突合して候補を出す
3. 初回のみ全件相当を取得（90日超の遡りは画面側で全件再取得、とブリーフに記載あり）

現在の `fetch` アクションは直近30日の差分から拾う暫定実装です。§3で件数と項目が分かり次第、
キャッシュ方式へ切り替えます。
